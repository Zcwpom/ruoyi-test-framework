【缺陷标题】用户名含 <script> 标签时，接口返回成功但入库值被静默改掉

【所属模块】系统管理 / 用户管理
【接口】POST /system/user
【严重程度】低

【复现步骤】
1. 登录获取 token

2. 新增用户，userName 里带一个 <script> 标签：

```bash
curl --location --request POST 'http://localhost:8080/system/user' \
     --header 'Authorization: Bearer <token>' \
     --header 'Content-Type: application/json' \
     --data-raw '{"userName":"xssprobe00281493<script>","nickName":"XSS探测","password":"Test@123456"}'
```

3. 查一下这条记录到底存了什么：

```bash
curl --location --request GET 'http://localhost:8080/system/user/list?pageNum=1&pageSize=500' \
     --header 'Authorization: Bearer <token>'
```

【预期结果】
两种处理都可以接受：
- 方案 A（推荐）：直接返回明确错误，告诉调用方用户名里有非法字符
- 方案 B：清洗之后再入库，但要在响应里说明输入被改过

不应该「返回成功」又什么都不说。

【实际结果】
接口返回 HTTP 200，业务 code=200「操作成功」：

```json
{"msg":"操作成功","code":200}
```

但查库发现实际存进去的 userName 是 `xssprobe00281493` ——
**`<script>` 这一段被剥掉了，和提交的值不一样，接口没有任何提示。**

```
提交值：xssprobe00281493<script>
实际存储：xssprobe00281493
```

补充说明（这点我验证过，避免夸大）：
**这不是 XSS 存储漏洞。** `<script>` 被过滤器剥掉了，没有写进数据库 ——
我翻了全表用户，搜不到任何带 `<script>` 的用户名，所以安全上是有防护的。
问题在于「静默修改输入值」：提交 A、存了 B、返回成功，调用方无从得知。

【影响】
1. 调用方以为创建成功的就是自己提交的那个名字，实际不是，排查问题时容易走弯路
2. 如果后续用提交的 userName 去查询/关联，会出现「按提交值查不到」的情况
3. 属于接口契约问题，不影响安全性
4. ★ 实测到的连带影响：我自己的自动化用例里有一个「数据清理」步骤，
   是按提交的 userName 去查并删除的 —— 结果因为名字被改写了，按原值查不到，
   脏数据就留在库里（实测残留了 userId=187、194 两个用户）。
   也就是说，静默改写输入值不只是「看着别扭」，它会让所有依赖这个输入值的
   下游逻辑一起失效。

【建议】
首选在 @Xss 校验里直接拒绝并返回提示（而不是放行之后再清洗）；
如果不能改，至少在响应里带上清洗后的实际值。
